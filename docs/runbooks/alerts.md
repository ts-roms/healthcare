# Alerts: what to watch and what to do

The conditions worth an alert, written against the signals the platform emits (`docs/architecture/observability.md`)
so they can be entered into whichever telemetry backend the organization chooses. No rule here is enforced by the
repository; thresholds are starting points, to be adjusted to the facility's volumes. Every alert should name the
process (`service.name`: `healthcare-api`, `healthcare-notification-worker`, `healthcare-integration-worker`).

| Condition                  | Signal                                                                                                         | Start with                                    | First action                                                                                                                           |
| -------------------------- | -------------------------------------------------------------------------------------------------------------- | --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| API down                   | `GET /api/v1/health/live` fails; no `http.server.request.duration` samples                                     | 2 failed probes a minute apart                | Platform logs for the crash; `http.unhandled_error` lines before it; restart is the platform's job                                     |
| Database unreachable       | `/ready` → 503; `outbox.relay_failed`                                                                          | Any                                           | PostgreSQL service and its connection limit; nothing is lost — writes fail fast, the outbox resumes                                    |
| Redis unreachable          | `/ready` → `degraded` with `redis: unreachable`; `rate_limit.redis_unreachable`, `realtime.redis_unreachable`  | 5 minutes                                     | Redis service; rate limits are off meanwhile (account lockout still applies), live updates fall back to polling, queues stop           |
| Object storage unreachable | `/ready` → `degraded` with `objectStorage: unreachable`; `queue.job_failures{queue.name="lab-report-archive"}` | 5 minutes                                     | Storage credentials and endpoint; uploads and report archives fail until it is back, lab release itself is unaffected                  |
| Errors                     | `http.server.request.duration` with status 5xx; `http.unhandled_error`                                         | > 1% of requests over 5 minutes, or any burst | Open the trace by `traceId` from the log line; every 5xx is a bug or a dependency failure                                              |
| Slow requests              | `http.server.request.duration` p95 per `http.route`                                                            | p95 > 2 s for 10 minutes on a staff route     | Compare `db.client.operation.duration` and `db.client.connection.pending_requests`: the pool, a missing index, or the dependency       |
| Outbox falling behind      | `outbox.oldest_age`                                                                                            | > 300 s for 5 minutes                         | A handler failing repeatedly (`event.handler_failed` with the same `eventId`) or the relay not running; events are retried, none lost  |
| Events parked              | `event.handler_failures{event.parked="true"}`                                                                  | Any                                           | The event gave up after `OUTBOX_MAX_ATTEMPTS`; find it in `domain_event` (`failed_at` set), fix the cause, reset `failed_at` to replay |
| Queue backing up           | `queue.depth{queue.state="waiting"}`                                                                           | > 100 for 10 minutes                          | The worker for that queue is down or slow (`/ready` on its `HEALTH_PORT`); notifications and exchanges wait, nothing is dropped        |
| Queue failures             | `queue.depth{queue.state="failed"}` rising; `queue.job_failures`                                               | > 10 in 10 minutes on one queue               | `queue.job_failed` lines name the downstream (SMTP, push, the integration partner); final failures surface in `/admin/integrations`    |
| Reconciler failing         | `queue.reconcile_failures`; `queue.reconcile_failed`                                                           | 3 in a row                                    | Usually the database from the worker; stranded work waits until it runs again                                                          |
| Telemetry silent           | No metrics from a process for 5 minutes while `/live` answers                                                  | 5 minutes                                     | The endpoint or its credentials (`OTEL_EXPORTER_OTLP_HEADERS`); the process keeps working without telemetry                            |
| Many sign-in refusals      | `GET /rate-limits/refusals` (platform administrators, `/admin/security`)                                       | Judgement                                     | `docs/security/access-control.md`: shared addresses vs. an attack; the counts carry no address or account                              |

What is deliberately not alerted on from telemetry: anything clinical. Critical laboratory results, overdue
referrals and quality notices are workflow notifications to staff (in-app), not operations alerts.
